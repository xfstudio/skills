# Octop 与淘宝平台操作参考

下列是 2026-10-29 在福客版 50362 和淘宝开放平台页面观察到的流程，界面及平台规则可能变化；以本次实际页面、权限和回执为准。此文件不是对真实写入的授权。

## 当前 BM 入口与只读观察

先按 [BM 本地发现](bm-preflight.md) 区分 BM 聚合根、Octop 内嵌 API 和独立 `bm-ai-taobao-topapi/services/employee-skill-api`；源码存在不证明运行时可用。部署 origin 从当前会话和页面核实，不把端口 50362 等同 localhost。2026-11-19 只读观察中，BM 的已登录入口为局域网 origin `http://192.168.110.121:50362/`，淘宝技能列表现有登录可用；这些是环境证据，不是默认账号、目标或未来部署承诺。

同日淘宝列表显示 335 项、每页 12 项、共 28 页。查看一个已有技能的详情确认正式 code 和定向订购表单，不能据此确认其他技能、整表查重或任何写入结果。技能卡片的操作按钮可能需先 hover，遮罩拦截点击时观察当前状态再操作，不盲目重复。未来账号与数据量以本次回读为准。

同次只读核查中，一个已有技能的授权弹窗起初显示“暂无授权店铺”，加载完成后实际有 2 家店铺；该样本弹窗未见分页。先等待加载结束并回读稳定列表，不能把过渡空态当作无授权、据此补授权，或把该样本无分页推及其他对象。此次仅查看现有页面，未上传包、修改表单、提交、增删授权，不能作为写入能力已验证的证据。

旧 adapter 在检测到分页时查找会返回 null；其 `submitListing` 仍会抛出 `TARGET_SCOPE_UNVERIFIED`。null 不是“平台不存在”，不能据此创建；该 adapter 不能证明完整分页查重或目标店铺核验。需要以当前 UI 翻页/筛选并记录覆盖范围、具体对象及编码；不能完成查重则停止创建，不能验证授权范围则停止相关提交，不修改 adapter 绕过保护。仅源码检索也不能证明平台能力已部署或启用。

## Octop 准备与记录

- 技能广场 → 技能包 → 批量导入 ZIP；按项目检查包完整性和导入回执。包大小等限制以当前服务为准。
- 在技能扩展表单准备名称、编码、类目、简介、示例、功能、输入输出、图标等。保留用户原始资料；本地拟用编码与平台正式编码分开，平台回读后才登记映射。
- 若当前部署提供 `/api/v2/bm/management/taobao-batches`，可使用其固定表单、包摘要、账户、环境和版本，按 API 实际定义记录各项状态。更新要使用当前 revision；冲突先重读。创建结果回读账号和实际编码后，按当前 API 契约确认绑定。
- 对已有批次和历史记录先读取再操作。批次的 `created`、`review`、`listed` 分别代表创建已核实、上架审核中、已上架；不得将版本审核中写作商店审核中。缺少精确回执或查询范围不完整时使用待核对状态。
- 工作树里的旧浏览器 runner/adapter 曾有暂不支持目标店铺检查等限制；不要假设它能处理本文件的整个流程，只有核实现版本确实支持且权限匹配时才复用。

## 淘宝技能创建与版本

1. 技能管理 → 创建技能；核对账号、名称、code、类目，选“上传技能包创建”，上传与固定摘要一致的 ZIP。
2. 平台列表中的草稿如果无法打开上架详情，列表可帮助定位，但不能单凭摘要文本断言正式 code 或所有未读草稿均不冲突。查找覆盖所有页；无足够证据时停止新建，按具体对象核对。
3. 进入技能编辑页检查工作区与 `SKILL.md` 是否导入，再通过“发布”提交版本；使用“版本管理/版本记录”回查版本与审核状态。列表草稿、版本审核、商店上架审核是不同阶段。
4. 版本可上架后打开“去上架”，读取不可编辑的技能 code 和目标账号，确认与 Octop 本地映射一致。名称、简介、功能、使用示例、输入输出、图标、订购方式以实际页面必填及长度规则为准。

## 上架与授权

- “上架到技能商店”页面曾默认选择公开订购；定向任务必须显式选择“定向订购”并检查状态。该表单曾不显示店铺名单，不能据此认为具体店铺已授权。
- 页面曾要求技能名称、简介、预置 query、功能与示例、图标等，并提供图片裁剪。具体要求以当下页面为准。曾出现服务端错误“一句话介绍仅支持中文、英文、数字、下划线”；校验失败时按平台提示修正并保留语义，不扩展到未经证实的其他字段。
- 用户阅读并处理协议；需交还时遵循 ego-browser 的 handOff 与恢复流程。提交后独立回看对应技能卡片和详情；“上架成功”提示仍需区分“审核中”和“已上架”。
- 定向技能显示“已上架”后，卡片“更多 → 授权管理 → 添加授权店铺”曾允许用英文逗号或换行分隔店铺名称。先读取已有列表，只添加本次目标中缺失的店铺；提交后回读确认店铺名称和条数。此为技能授权，不等于员工可见名单、版本灰度名单或商家订购成功。
- 核查授权列表的全部页面或可用筛选范围；无法完整读取时不要断言某店铺不存在。店铺同名或身份不明时先核实平台可用标识。部分添加成功时分别记录成功、失败和未知项；只对已确认未生效的项处理，未知项先对账。回读失败时标记结果未确认。

## 状态与对账

| 实际现象 | 应记录的结论 | 下一步 |
| --- | --- | --- |
| 创建前无法核实现有草稿编码 | 查重不完整 | 查证该对象或请求针对该对象的确认 |
| 提交超时或结果不明 | 待核对 | 查账号、对象、版本、记录；未排除在途前不重试 |
| 版本审核中 | 版本审核中 | 等待或按用户要求跟进 |
| 定向、审核中 | 商店上架审核中 | 等待审核，不宣称已上架 |
| 定向、已上架 | 已上架 | 读取授权管理并核对指定店铺 |
| 店铺列表包含指定店铺 | 平台显示已授权 | 如需实际使用验收，再在商家侧验证 |

记录可供回查的技能名称、账号、正式 code、动作、平台状态、时间、目标店铺及页面或回执证据，不记录凭据。平台拒审时保留原因并说明，不自行重提；上架后商家不可见时分别检查授权、商家身份、订购和客户端，不能用单一状态推断原因。超时是否可重试取决于平台记录和在途请求的实际证据，等待固定时长本身不能证明请求失败。

可将已授权任务的异步审核跟进交给任务调度；只有用户要求跟进时设置，避免重复监控和无变化提醒。需要员工接口时，另外核对员工可见范围及平台要求，不能把店铺名未经确认当作必然等同主账号 displayNick。
